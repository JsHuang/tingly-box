# Frontend i18n: one file per namespace

## Layout

```
frontend/src/i18n/
  index.ts                 # i18next init, SUPPORTED_LANGUAGES
  locales/
    en/                    # fallback bundle
      index.ts             # imports every namespace file, exports one object
      common.ts            # → t('common.*')
      provider.ts          # → t('provider.*')
      ...
    zh/  ru/               # same file set as en/
```

A namespace file is named after the **first segment of the t() key** it
holds: `t('rule.routing.title')` lives in `locales/<lang>/rule.ts`. To find a
string, take the key's first segment and open that file in each language.

## Why plain modules, not i18next namespaces

i18next can load several namespaces (`useTranslation('rule')`,
`t('rule:routing.title')`), but switching to them would change every one of
the ~hundreds of `t()` call sites and the `tKeyCoverage` scan. The size
problem is only in the source files, so the split stays there:
`locales/<lang>/index.ts` reassembles the same single `translation` resource
object i18next has always received. Runtime behaviour, key paths and
`index.ts`'s `resources` are unchanged; the split was verified by bundling
each locale before and after and comparing the JSON byte for byte.

All locales are still bundled eagerly. Lazy per-language loading
(`i18next-resources-to-backend`) is a separate decision if bundle size ever
matters.

## Adding strings

- A key under an existing namespace: edit `locales/<lang>/<ns>.ts` in every
  language (`localeParity.test.ts` and `tKeyCoverage.test.ts` enforce it).
- A new top-level namespace: add `<ns>.ts` to each language directory and a
  matching import + entry in each `locales/<lang>/index.ts`.
